# RailMate BD — source and CI repository

P41 corrective source targets signed release `v1.0.0+28` on `main` only — no PRs, feature branches or worktrees. Owner setup and teacher acceptance remain pending where noted below. The `RailMate-BD-internal` repository holds requirements and evidence. Read `AGENTS.md` before any task.

## What the app does

A Flutter Android app against hosted Supabase. **Splash → Onboarding → Welcome → Login/Register → Verify → Home** is a real startup state machine (`lib/app/app_gate.dart`), not an unconditional home route.

Search covers **24 demo stations and 32 services**, with a today..+20-day picker, GraphQL-first stations, actual bundled TFLite ranking and demo-hold-aware seat maps. The hosted timetable is synthetic and requires owner-side horizon refresh; dates are not automatically kept current by the app. Booking is **atomic and multi-seat (1–4)** through deployed `book-trip` / `cancel-booking` Edge Functions after a simulated payment (**no real money**); QR+PDF tickets state **DEMONSTRATION ONLY / NOT VALID FOR TRAVEL**. Journey Board supports realtime comments, reactions and ratings plus cursor pagination, **multi-format attachments** (up to 10 images/videos/documents/links per post) and **permanent post links** (`railmatebd://post/<uuid>`, public web permalink). The guide bundles a licensed video and uses Leaflet/OpenStreetMap; maps and GSAP need reachable CDNs. Account-scoped OpenRouter BYOK "Improve Wording" sends the key only on an explicit, consented action. Bottom tabs: Home / Bookings / Board / Profile.

Stack: Flutter Android, hosted Supabase (Postgres/Auth/Storage/Realtime/REST/pg_graphql/Edge Functions), OpenRouter BYOK, tiny TFLite search model, plus a static **GitHub Pages** viewer (`site/`). **No Docker, no local application DB.** This repository cannot sell real railway tickets.

Live backend config passes only via `--dart-define` (`SUPABASE_URL`, `SUPABASE_ANON_KEY` / `SUPABASE_PUBLISHABLE_KEY`); CI reads the same names from repository variables. Booking and payment need no app-side secrets — the service-role key stays server-side.

## Honesty rules this app holds to

* Every timetable, fare, occupancy figure and ticket says **DEMONSTRATION ONLY**; nothing claims official Bangladesh Railway accuracy.
* The demo timetable is synthetic and generated by `refresh_demo_horizon()` (owner/admin only, idempotent, never writes `booking_id`). New-station coordinates are synthetic placeholders and are not used for navigation.
* Loading, empty, error and offline states are real and distinguished: a timeout never renders as "no trains", a failed load never presents zeros as data, and a charted failure never fabricates rows.
* On-device ranking states which ranking produced the visible list — including when it fell back to unranked order.
* Social login remains explicitly unimplemented. P41 adds **Telegram contact-sharing verification** on Profile as the proposed alternative to SMS OTP. The app requires a verified backend row; no typed number or fake OTP counts as proof. Tokens are stored hashed, numbers are displayed masked, and `auth.users.phone_confirmed_at` is never changed. Bot configuration, migration apply, deployment and a real Telegram demonstration remain owner-side; teacher acceptance of the alternative is pending. The older Supabase SMS lane is retained but still needs an approved provider.
* Signup keeps email/password and username registration. Email confirmation uses a real six-digit Supabase token through Mailjet SMTP; paste, invalid-code retry and resend cooldown are supported. A late response cannot undo a newer logout. Password recovery remains link-based. Earlier packets recorded real disposable-inbox delivery and emulator OTP entry; P41 did not repeat that provider test.
